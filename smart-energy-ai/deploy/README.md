# Raspberry Pi deployment checklist

1. Copy the extracted project to the Pi (example: `/home/student/Smart-Energy-AI`). Confirm `uname -m` is aarch64 and Python version (`python3 --version`). Use 64-bit Raspberry Pi OS and Python 3.11/3.12 where possible.
2. `cd ~/Smart-Energy-AI`; `python3 -m venv .venv`; `.venv/bin/python -m pip install -r requirements.txt`; `.venv/bin/python -m energy_ai train-demo`; `.venv/bin/python -m energy_ai serve`. Install `python3-venv` using your package manager if missing. Scientific Python dependencies need compatible ARM64 wheels or appropriate system packages; install can be more demanding on older Pi models.
3. Open the Pi browser at `http://127.0.0.1:8000`. From Windows, use `ssh -L 8000:127.0.0.1:8000 student@PI_IP` then open the same URL locally. Replace PI_IP and user with actual values. Keep the service on localhost; if network exposure is needed, use the existing approved authenticated reverse proxy/firewall, not an unrestricted `0.0.0.0` binding.
4. Fetch external weather manually at first: `.venv/bin/python -m energy_ai fetch-weather`. Once network access is validated, schedule this command with a systemd timer or cron at an approved interval (e.g. every 3 hours); monitor failures and use provider terms/limits. Cache older than 12 hours is rejected.
5. Export measured telemetry following the data contract and train a real model. Confirm exact location/profile and validate accuracy, missing sensor handling, clock sync, stale inputs, reliability and battery protections before use. The manual battery UI is not a trustworthy live reading. Implement live read-only database/TTN adapter with least-privilege credentials, authentication, TLS and freshness checks.
6. Optional systemd service template `energy-ai.service`: adapt user/paths, choose measured model flag when ready, then `sudo cp energy-ai.service /etc/systemd/system/energy-ai.service` (from this deploy folder), `sudo systemctl daemon-reload`, `sudo systemctl enable --now energy-ai`, `sudo journalctl -u energy-ai -f`. Confirm service runs with correct permissions. Do not run as root. Template starts demo model by default.

No physical Pi deployment was tested during prototype packaging. The API is advisory, not a battery safety controller.
