# Daily learning planner — team profile and prediction reliability

## Purpose and status
The final daily application predicts battery state of charge at 14:00, then estimates how many five-minute lessons and complete twenty-minute sessions can fit before 17:00. Charging and learning are mutually exclusive. The legacy hourly research dashboard remains at `/research` with its original simulation profile (500 Wh, 100 W); do not use its estimates as operational suitcase advice. The daily model uses a separate team profile. All hardware values and learning assumptions need validation.

## Team profile
Based on the supplied `battery_forecast_models-split.ipynb` text: 180 Wh battery, 25 W panel, 0.8 physical derating, 20-minute sessions, 10 percentage points per session, 14:00–17:00, maximum eight sessions (32 lessons, 160 minutes), per the latest teacher feedback; 20 minutes remain outside the learning allocation. One five-minute lesson is assumed to be one quarter of a session (2.5 pp). We retain a 10% **end reserve**, intentionally stricter than the notebook's 10% start threshold, which permits a session to start at 10% and finish at zero. Three hours is the scheduled learning window; 30 pp/h drain implies 200 minutes to theoretical zero, so the separately reported three-hour runtime is not treated as an exact zero-discharge measurement. The reported 11-hour charging time is a reference, not a fixed solar rate. Verify all these values with the hardware team.

## Data and training
`train-daily-demo` creates 365 synthetic charging-only days, eight prediction hours (06:00–13:00), 2,920 rows. Simulated solar input uses the team physical baseline (25 W × irradiance/1000 × 0.8, bounded by panel rating), random day efficiency, temperature effect and charging taper. Simulated weather and battery values are not the team's original CSV or actual hardware. Each day's target is the 14:00 battery. Features: current battery, hours remaining, radiation sum, average clouds and temperature, day of year. No charging-window usage is allowed. The complete team CSV is bundled and automatically trained by `train-all`; it remains generated prototype data. Standalone retraining: `python -m energy_ai train-daily-team --csv data/device_sessions_hourly_mock_long.csv`. It imports complete charging-only weekday windows using the notebook's end-of-hour battery convention and rejects invalid or duplicate rows. Select Team prototype dataset in the UI after training. The complete supplied CSV was imported and evaluated; see `team_evaluation.json`.

Chronological split: 219 training days, 36 model/margin selection days, 37 independent interval calibration days, 73 untouched test days. All predictions from a day stay together. TimeSeriesSplit on training days tunes Random Forest; compare average-gain baseline, Linear Regression direct/gain, Random Forest direct/gain. Select model and margin on 08:00 validation advice, targeting at most 5% over-advice of individual lessons and minimising lost lessons. Refit on training plus selection days; do not fit on calibration or test. The selected forest_direct uses 80 trees, max_depth=None, min_samples_leaf=3, and a 5 pp advice margin. The eight-session cap applies during selection and testing, not only in the UI. Results are in `daily_evaluation.json`.

## Prediction reliability
For each prediction hour, use absolute battery errors on independent calibration days. Sort errors; choose rank ceil((n+1)*0.90). The selected error radius is added/subtracted from the point prediction, bounded to 0–100%. If the rank exceeds the number of available calibration days, the interval is unavailable (no fabricated certainty). Report empirical coverage on held-out days, MAE, fraction within 5 pp, exact/over/under lesson and session advice. The nominal 90% target is not a guaranteed future probability; chronological dependence, forecast error, domain shift and mock data limit interpretation. The interval is separate from the advice margin. Live weather does not validate the model. The 08:00 radius is 6.11 pp; 67/73 simulated test values inside (91.8%); MAE 2.55 pp; 61/73 within 5 pp (83.6%). Baseline MAE 10.25 pp. Exact full-session count 43/73 (58.9%); too many full sessions 1/73 (1.4%); too few 29/73 (39.7%). Exact lesson count 30/73; too many lessons 1/73. These conservative estimates are not real learning outcomes. The team's notebook reports 1.2 pp MAE and 87% exact sessions on its own mock experiment; not reproduced here, different data and reserve rule.

## Learning advice and API
Usable battery = max(0, predicted battery - 10 pp reserve - selected margin). Complete lessons = floor(usable/2.5), capped at 32. Full sessions = lessons // 4, extra lessons = lessons % 4. Extra lessons assume they can be offered separately. No double counting. Recheck actual battery before learning via `/api/lessons/actual?battery_pct=80` (28 lessons, seven sessions with no forecast margin). A battery management system must enforce actual hardware limits.

`POST /advice` returns point forecast, `recommended_lessons`, `recommended_sessions`, `additional_lessons`, duration, charging window, reason, hardware profile, and `prediction_reliability` (range, coverage, MAE, rates, provenance). `GET /api/daily/reliability?prediction_hour=8` returns standalone historical reliability metrics. `GET /api/daily/metrics` returns full training report. `GET /api/daily/config` returns the central policy including the 8-session and 32-lesson caps. `GET /api/lessons/actual?battery_pct=100` returns 8 sessions, 32 lessons and 160 minutes. The frontend shows these separately and retains solar graphs, model comparison, error plots, JSON preview and manual/TTN input. All API paths are local prototype endpoints; do not expose publicly without authentication.

## Real measurements
Use `listen-ttn` with TLS and application credentials; see quickstart. Export logs with `export-ttn`. Use `prepare-daily-real --logs ... --weather ... --device-id ... --verified-days ...` for confirmed charging-only days with complete weather and recent battery measurements, then `train-daily-real --csv data/daily_real_training.csv`. Select measured model in UI. Verify hardware state of charge, charging current, exposure, lesson energy, timestamps, and location. Need at least 20 distinct days for training and at least nine calibration days per hour for a finite 90% interval; more diverse days strongly preferred. Archived forecasts available at prediction time are preferable to historical observed weather. Real TTN, hardware accuracy, live weather and actual student outcomes remain unverified. No real-world confidence percentage is claimed.
